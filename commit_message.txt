P0 FIX: Properly classify missing storage into repairable vs materialization paths

The previous implementation incorrectly assumed all missingStorage records were repairable via storage field mutation. This violates the architectural invariant that Drive records without Blob evidence require materialization, not storage repair.

ARCHITECTURAL FIX:

1. Audit contract now returns separate actionable categories:
   - repairableStaticIds: Local source with static manifest evidence
   - repairableBlobIds: Local source with full Blob evidence chain
   - requiresMaterializationIds: Drive source without Blob evidence
   - ambiguousIds: Insufficient evidence for any repair

2. UI shows actual safe action counts with separate buttons:
   - "Repair Static Records (X)" → submits repairableStaticIds
   - "Repair Blob Records (Y)" → submits repairableBlobIds
   - "⚠️ N Drive records require materialization via Drive browser panel"
   - "⚠️ M records require manual review"

3. Repair endpoint updated to skip Drive records without Blob evidence:
   - Changed skip reason from "insufficient evidence" to "requires Drive materialization (not storage repair)"
   - Makes clear that storage repair is NOT the correct operation for Drive records

4. Classification and repair evidence chains aligned:
   - Static: requires manifest evidence only
   - Blob: requires contentHash + Blob metadata + URL match + physical hash verification
   - Drive without Blob: never repairable via storage field mutation

INVARIANTS PRESERVED:

- Drive provenance alone NEVER implies Blob storage
- Storage field is not inferred from source type
- Public gate remains fail-closed for missing storage
- Repair mutations are explicit and targeted
- Drive materialization path is the correct operation for Drive source records
