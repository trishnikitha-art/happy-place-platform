# Advanced web-development roadmap — October 10, 2026

Research is ordered by problems observed in this application. No recommendation establishes faster Core Web Vitals without browser measurements. This is a bounded research pass, not a claim that every design trend has been exhaustively investigated.

## Implementation sequence

1. **Completed: content-aware loading.** Route-specific fallbacks, stable photo geometry, meaningful client operation feedback, reduced-motion CSS, responsive image hints, and server-provided reviews. See `LOADING_UX.md` for evidence and sources.
2. **Completed: native Workbench dialogs.** Add Visual Slot was a plain overlay with unnamed controls, no native modality, and no Escape handling. Both Workbench dialogs now use native top-layer modality, named fields, cancel focus, restoration to an existing workflow control, bounded scrolling, and a short optional entrance. Confirming a replacement moves focus to progress when its opener becomes disabled. Existing validation, explicit replacement confirmation, and all mutation gates remain intact.
3. **Implemented maintenance: Lenis.** Replace the deprecated package with maintained stable v1.3.26 and its recommended stylesheet. Keep the custom provider, native-scroll route policy, live reduced-motion handling, native touch input, and one manually managed animation clock. No React adapter rewrite or v2 prerelease was introduced. Deployment follows lifecycle, build, and browser checks.
4. **Next: measure navigation and component layouts.** Profile representative cold/warm routes and modest devices. Introduce container queries only where a reused component's actual container width causes a demonstrated layout defect. Prototype shared-element transitions in isolation if measurements and visual review show useful continuity.

## Dialog verification

Typecheck, scoped/repository lint, the full default Jest suite (1,083 passed / 26 skipped), production build, and image QA passed. Browser checks used the actual dialog components and compiled CSS in an isolated localhost fixture. Both dialogs opened with cancel focus; Escape canceled without confirming. A disconnected context-menu opener restored focus to the Page selector. Confirm disabled the replacement opener and focused the stable operation status instead. Closing restored the prior body overflow. Native modality kept background controls inert; browser chrome can still receive Tab focus.

A 20-target dialog stayed within 85dvh at 1440, 1280, 768, and 390 pixels without internal horizontal overflow. Keyboard navigation scrolled its bottom controls into view while the page stayed at scroll position zero. Mobile preview details use two rows to leave the filename readable. The optional 160ms opacity entrance is scoped to no-preference. Reduced-motion browser override and physical Safari/touch-device testing remain unverified.

## Lenis maintenance scope

The lockfile changes only the deprecated package entry and the maintained replacement. `lenis` v1.3.26 retains this provider's constructor options, millisecond `raf`, `destroy`, and `on`/`off` subscription API. `autoRaf: false` explicitly keeps the provider as clock owner. Existing parallax cleanup remains intact. The [versioned core](https://github.com/darkroomengineering/lenis/blob/v1.3.26/packages/core/src/lenis.ts), [versioned stylesheet](https://github.com/darkroomengineering/lenis/blob/v1.3.26/packages/core/lenis.css), and npm stable dist-tag were checked. CSS supplies root sizing and nested overscroll containment; native CSS smooth scrolling stays disabled while Lenis owns scrolling.

Lifecycle tests cover repeated mount/unmount, query-only preview changes, route disposal, animation cancellation, initial reduced motion and live preference changes. New checks specifically guard against enabling the library's second animation clock or synchronizing touch motion. No claim of better frame rate or lower INP is implied by a dependency update.

Browser review found an upstream disposal edge case: native keyboard scrolling schedules a velocity reset, and `destroy()` does not cancel that timer. After navigation it could restore a stale Lenis root class. The provider now calls the supported `stop()` before `destroy()` to reset scrolling state, so the delayed callback cannot change the class state. A lifecycle regression check enforces that order; the actual route transition is checked in the browser.

Final typecheck, scoped/repository lint, production build, image QA and full default Jest passed (1,086 tests / 26 skipped). On the rebuilt local app, keyboard scrolling followed by gallery navigation kept Lenis classes cleared through opening/zooming/closing a lightbox. Back/forward restored the smooth homepage/native gallery policy, and `?workbench=true` remained native. The skip anchor changed the fragment with native CSS behavior; the fixed header stayed at the viewport top. At 390px the existing menu opened as a native modal with an independently scrollable, contained panel; Escape restored its opener. Workbench authorization still established the isolated local editor session. These are local behavior checks; physical Safari/touch and performance measurements remain open.

## Next measurement protocol

Use the same production build conditions, browser version, viewport, network/CPU settings and test location for before/after comparisons. Keep cold cache and warm cache in separate groups, repeat runs, and report median plus spread. Record the exact SHA, path, viewport and delivered image candidates/bytes. A localhost fixture does not reproduce Vercel image caching or visitor conditions.

- **Hard navigation:** Lighthouse Navigation mode on homepage, archive, a project detail, services and contact. Identify the actual LCP element and request timing; scroll the image-rich content to inspect layout shifts. Inspect whether `sizes` selected a sensible candidate rather than assuming Next Image or native `<img>` is faster. [Lighthouse modes](https://developer.chrome.com/docs/devtools/lighthouse), [Next 15 Image](https://nextjs.org/docs/15/app/api-reference/components/image).
- **Client navigation:** Lighthouse Timespan / Performance recording through real links and back/forward. Hard loads and App Router route transitions are different measurements. Inspect menu, gallery/filter, and form interactions for long tasks and local input latency. [Chrome Performance panel](https://developer.chrome.com/docs/devtools/performance/overview), [SPA measurement caveats](https://web.dev/articles/vitals-spa-faq).
- **Field outcomes:** Use available CrUX or deliberately approved RUM, segmented by device at the 75th percentile. Good targets are LCP ≤2.5s, CLS ≤0.1 and INP ≤200ms. Lab samples cannot establish visitor distributions, and CrUX's rolling 28-day data cannot verify an immediate release effect. [Lab versus field](https://web.dev/articles/lab-and-field-data-differences), [field measurement practices](https://web.dev/articles/vitals-field-measurement-best-practices), [LCP](https://web.dev/articles/optimize-lcp), [CLS](https://web.dev/articles/optimize-cls), [INP](https://web.dev/articles/optimize-inp).

Measure first because the loading and dependency changes are complete enough for a useful baseline; adding speculative transitions, virtualization or visual effects before locating a real bottleneck would not establish value.
